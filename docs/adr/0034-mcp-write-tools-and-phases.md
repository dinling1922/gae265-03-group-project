# MCP 開放寫入：`write` 權限範圍、自然語言建立推薦、暫時上傳票、分兩階段

[ADR-0032](0032-mcp-server-with-access-tokens-read-only.md) 第一版只讀，並寫明寫入類工具要另做設計；[ADR-0033](0033-line-bot-adapter-over-mcp.md) 的 LINE bot 也只讀。使用者要讓外部 AI 助理做到：輸入地點與需求就產生保險方案（功能一）、詢問推薦方案的細節、再進到保單問答與建立理賠待辦（功能二）。這份記下寫入怎麼授權、哪些工具、哪些不做，並分兩階段：A（功能一）先做，B（功能二）規格先寫好、確認後再做。

## 決定

- **新增 `write` 權限範圍**：`api_token.scopes` 本來就預留。建立權杖時要在帳號頁明確勾選「允許建立資料」，預設仍是唯讀；寫入工具檢查範圍，唯讀權杖呼叫被拒。LINE 綁定的權杖一律唯讀，LINE bot 不新增寫入指令。寫入工具只做「建立或更新使用者自己的紀錄」，不刪除、不送件、不碰 Drive 與 Gmail（[ADR-0025](0025-claim-submission-fill-before-send.md) 的邊界不變）。
- **工具可以各自設定權限範圍與限流**：註冊工具時指定所需範圍與每分鐘上限（呼叫後端 LLM 的工具另設較低的上限）。
- **自然語言建立推薦（階段 A）**：`create_comparison(request, overrides?)`，`request` 是使用者的原話。後端用 LLM（結構化輸出）**只做抽取**：目的地（限 16 個選項）、出發與回程日期、最多 3 個在意事項（依重要程度排序）。抽取結果一律經列舉值與日期驗證，不合格就視為資訊不足。資訊不足或不明確時**不猜、不建立**，回 `status: "needs_more_info"` 與缺什麼，由 AI 去問使用者；成功時回傳「LLM 理解的內容」與推薦結果，讓 AI 先給使用者核對。相對日期以台北時間的今天推算，「五天」含首尾（回程＝出發＋4 天）。不支援的需求（例如「最便宜」「我 70 歲」）明確回報不納入。推薦與數字仍全由程式決定（[ADR-0004](0004-llm-never-produces-numbers.md)），LLM 不產生任何數字；不預覽、不拆兩步，建錯就再建一筆。
- **方案細節（階段 A）**：`get_plan_details(plan_id)` 唯讀回傳保障明細、可選保額與保費（程式資料）；`ask_plan_question(comparison_id, question, history?)` 沿用網站 1-4 的方案問答（依條款回答、附條文出處、沿用現有 guard，不存檔），行為與網站一致（針對該次比較的推薦方案與次推薦）。另有唯讀的 `list_options`，回傳可用的目的地與在意事項。
- **暫時上傳票（階段 B）**：MCP 不收檔案。`request_policy_upload` 回傳一個深層連結，導向網站現有的保單上傳步驟，帶一次性、15 分鐘有效、綁定使用者的票；仍要正常登入，登入者必須是票的擁有者，解析結果也由使用者本人在網頁確認。AI 用 `get_upload_status`／`list_policies` 看結果。
- **事件與待辦（階段 B）**：照搬網站流程：`create_incident`、`send_incident_message`（回 5 號 agent 的回覆與待辦）、`confirm_incident`。事件預設未確認，確認後待辦才計入；工具說明要求 AI 必須先取得使用者明確同意才能確認。呼叫的是和網站同一套 5 號契約，不改 agent，成本計入限流。**待辦不開放 AI 勾選**：LINE 與 AI 只能查待辦與文件的狀態（有無打勾、文件辨識狀態），要處理文件或待辦就引導回網站。
- **保單（階段 B）**：除了上傳，也提供網站「手動選公司與方案」同樣的建立方式（`create_policy_manual`），只是記錄使用者買了什麼，不是投保（GLOSSARY：只做推薦與問答，不經手投保）。`ask_policy_question` 依使用者保單的條款回答並附出處。
- **輸出仍用允許清單**：不回保單號碼、被保險人姓名、檔名、Drive 連結；事件自由文字只回 agent 的回覆與待辦。

## 取捨與沒選的做法

- **獨立的寫入端點、或所有權杖都能寫**：前者多一套部署與驗證，後者外洩影響太大；用範圍最小。
- **後端不用 LLM、由客戶端 AI 對應選項**（原本的建議）：成本與出錯面最小，但使用者選擇讓後端抽取，換取客戶端不必知道選項細節；代價是後端多一個 LLM 呼叫，要有限流與驗證。
- **MCP 直接收 base64 的 PDF**：保單是個人資料（[ADR-0009](0009-policy-document-personal-data.md)），經客戶端 AI 的對話會進第三方 LLM，且吃對話 context。
- **上傳票免登入**：等於把一次性密碼放進對話，解析結果又該由本人確認，不選。
- **AI 勾選待辦**：誤判會影響送件檢查，另案。

## 後果

- 有 `write` 權杖外洩的風險比唯讀高：建立的是使用者自己的比較紀錄與保單／事件，不能刪除與送件；稽核照樣記每次呼叫。
- `create_comparison` 呼叫 Azure OpenAI，要有每分鐘上限與失敗時的明確錯誤；LLM 抽取的準確度需要小量評估題組（目的地、相對日期、在意事項）。
- 階段 B 依賴 5 號 agent 的契約與網站上傳頁的深層連結改動，確認後才開始。
