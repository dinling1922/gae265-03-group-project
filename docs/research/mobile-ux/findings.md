2026-11-15。依 [walkthrough.md](walkthrough.md) 的清單走查，原始紀錄在走查頁（Artifact，資料庫 `walk/state`）。這份文件整理結果、嚴重度與建議開的票；票都還沒開，要先經使用者確認。

量測只碰 `localhost:5173` 那一個分頁。截圖與其他分頁沒有留存。

## 判斷標準

沿用 walkthrough.md：沒有橫向捲動、固定元素不被遮、`dvh` 而不是 `vh`、點擊目標至少 44px、輸入框字級至少 16px。

## 結論

直式走完整個流程沒有擋住的問題。問題集中在三處：**橫式**（彈窗、補充畫面、問答面板）、**`vh` 與網址列**、**小於 44px 的點擊目標**。沒有「擋住」層級的問題，目前都是「難用」。

## 發現

嚴重度：擋住、會誤操作、難用、小瑕疵。

### F1 現況確認彈窗在橫式被切（難用）

- 步驟 4a，橫式、網址列顯示時，可見高度 337px，彈窗高 377px，垂直置中後頂端超出畫面 20px（標題被切）、底端超出 19px。
- 原因（量測確認）：`DialogShell` 的 `max-h-[90vh]`（`frontend/src/components/ui/DialogShell.tsx:44`）。實測 `max-height` 是 376.985px，等於 419px 的 90%；419px 是網址列收起時的 `vh`，比實際可見高度大。直式同一頁 `100vh` 是 920px、`100dvh` 是 839px，差 81px。
- 彈窗內容 475px，彈窗內部可以捲動，兩個按鈕（y 281 到 329）仍在可見範圍內，所以還按得到。
- 影響範圍：`ConfirmDialog` 用 `DialogShell`，所有用 `DialogShell` 的對話視窗同一個問題。`UploadPreview.tsx:130` 的 `max-h-[60vh]` 是同類用法，但值較小，目前沒被切。
- 建議：`DialogShell` 的 `90vh` 改 `90dvh`（一處修，全部對話視窗受益）；`UploadPreview` 一併改。改完在橫式與直式各看一次。

### F2 2-2 補充畫面在橫式加鍵盤時，「回到確認」被蓋住（難用）

- 步驟 4a，按「還要補充或修改」後的 `ClarifyingView`。橫式鍵盤開著時，可見視窗只剩 89px 高；輸入框（y 286 到 338）和「送出」在範圍內，「回到確認」與「回首頁」（y 391 到 439）被鍵盤蓋住，要先收鍵盤再捲動才按得到。直式沒有這個問題。
- 這就是走查備註「橫向時不允許做上一頁動作」的原因。
- 建議：把「回到確認」移到輸入框同一列或上方（橫式時不用往下捲）。要先和設計者確認位置。

### F3 行程頁問答面板在橫式版面跑掉（難用，未在本機量測）

- 步驟 6，橫式。使用者截圖看到聊天泡泡與下方「回答由 AI 依條款整理，實際以保險公司審核為準。」文字重疊，聊天區卡片與外層白框對不齊，輸入框不在畫面內，要在面板裡再捲動。
- 可能原因（讀 `main` 程式碼，沒量到）：`frontend/src/features/trip/TripPage.tsx:378` 的手機面板是 `max-lg:h-[50dvh] max-lg:overflow-y-auto`，橫式高度只有約 200px；裡面的 `DescribeChat` 設了 `minHeight={180}`、`tall`、`fill`，加上標題與說明，總高超過面板。橫式寬度也不到 `lg`（1024px），仍走手機版版面。
- 截圖來自哪個站台沒有確認，本機分頁當時停在 2-2。要在本機開到行程頁、打開問答面板後橫式量一次再下結論。
- 建議：先量測確認；方向可能是橫式時面板改成靠側的欄位，或高度改用較大的比例並讓聊天區自己捲動。

### F4 點擊目標小於 44px（難用）

首頁量到 6 個，直式：

| 元素 | 尺寸 |
| --- | --- |
| Logo「好險有你」 | 155×39 |
| 「後台」 | 28×22 |
| 使用者名稱連結（到我的帳號） | 85×22 |
| 「登出」 | 45×22 |
| 「看全部」 | 58×18 |
| 頁尾「開發工具」 | 332×23 |

- 「後台」與「開發工具」推測只有管理者與開發環境看得到（沒有查程式碼確認），一般使用者遇到的機率較低，優先度較低。
- 使用者名稱連結與「登出」兩個相鄰的小目標，誤觸風險最高，建議優先。
- 建議：手機版導覽列的連結與按鈕補到至少 44px 高（加 padding 或 `min-h-11`），不一定要改字級。

### F5 安全區域沒處理（待驗）

- `index.html` 的 viewport meta 是 `width=device-width, initial-scale=1.0`，沒有 `viewport-fit=cover`；四邊 `env(safe-area-inset-*)` 都是 0。
- 在 Pixel 直式沒有影響。橫式內容沒有畫進鏡頭與狀態列區域（左邊與上方黑條），沒有被遮，只是版面較窄。
- 有瀏海或圓角的機型（iPhone）才會真正遇到，等 iPhone 補跑再決定要不要開票。

## 不是問題

- **步驟 9 與 11 的離線**：先前用飛航模式測，結果上傳與送件「還能往下走」，是測試方法造成的。`adb reverse` 走 USB，飛航模式斷不了這條通道，請求其實有送到伺服器。改用除錯介面模擬離線後：
  - 步驟 9：頁面顯示「上傳完成，共 1 份：0 份已自動打勾、1 份上傳失敗」與「連線中斷，上傳失敗」。
  - 步驟 11：按最後送出，顯示「連不到伺服器，請稍後再試。」並停在送件頁。
  - 結論：兩處對離線都有處理，不是 agent 6、7 沒檢查網路。
- **輸入框字級**：2-2 補充畫面的輸入框 16px，在 Android 上沒有被放大；字級小於 16px 的放大行為主要出現在 iOS Safari，要等 iPhone 補跑才能確認。首頁沒有輸入框。其他頁的輸入框沒逐一量。
- **橫向捲動**：量過的頁面都沒有。
